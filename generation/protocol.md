# Goal-driven School generation protocol

You are generating a course, not teaching a student yet. Read the input JSON and the available original local sources before proposing knowledge claims. For multi-page documentation captures, follow the derived-copy and provenance rules below. Use the same protocol for repositories, papers, and other materials. Do not modify anything outside the specified output school, and do not run git commands, publish, install packages, or change infrastructure. If tools or checks appear incorrect, report them instead of modifying them.

1. Translate the learning goal into observable learner capabilities. Work backward from a small transfer activity. Select only prerequisites that enable those capabilities. Use the supplied depth, background, learningStyle, and original natural-language request as actual curriculum design constraints. If unspecified, use a systematic conceptual route with beginner-friendly scaffolding. For an introductory request prioritize core intuition and small concrete activities, omitting mechanisms that do not help the goal. A deeper request should change the capabilities, selected mechanisms, derivations, boundary cases and activity complexity, not merely length or labels. Assume only the explicitly supplied background; explain remaining prerequisites in place. Free-text depth requirements are valid; there is one generator, not separate generators per depth. Do not confuse curriculum depth (what to learn) with teachingMode (how to teach).
2. Inspect sources with targeted searches and reads. For code, identify actual symbols, branches, and relevant tests in the supplied version. For documents, read the relevant text, equations and figure descriptions. Distinguish source-supported statements from your own analogy, generated example, inference, and uncertainty. No invented citations. Copy each referenced original source file unmodified under public/sources/ using its relative path within the input source root. This allows any teacher to read the saved original locally via HTTP. For crawled Markdown derivatives, follow the multi-page capture rules below. Present factual grounding in lesson prose through `{{cite}}` markers (linking verbatim quotes to original URLs and saved local files), list referenced files in frontmatter `sources`, and point teachers to `{origin}/sources/...` paths and precise symbols/sections/equations in `agentInstructions`. Put source management metadata (version, retrieval/crawl date, tool, derived status, `entry.html`) in `COURSE.md` selected sources and `provenance.json`, never in lesson prose. Extracted text is a derived reading aid, not the original PDF/HTML; preserve and reference saved originals alongside it. Do not claim that an original was saved when only a derived copy is available. The source root may include documents and supplementary official documentation; choose the minimal relevant subset. PDF copies are useful for humans, but provide extracted text for the teacher. Do not copy entire repositories. Do not claim to have read an inaccessible source, or add outside sources without actually retrieving/reading them and recording their provenance. If the current model and its available tools support visual reading, before writing any lesson, first open and visually inspect at least one source page image or illustration relevant to the planned course, then inspect the other visuals the course depends on (use an image such as PNG/JPG if reading the PDF returns only extracted text; extracted text does not count as seeing a page); if visual access is genuinely unavailable, continue from the available text and record in COURSE.md what was not read visually, which files and page numbers can be confirmed, and why. If a figure number cannot be confirmed, say so. Do not invent content from filenames, do not claim to have seen pages when only text was read, and do not stop generation for lack of vision. This does not cancel the existing material-preparation failure when extracted text is too little.

When a material record contains `crawl` without `crawl.fallback`, that directory is a multi-page documentation capture. Read `provenance.json`, then use targeted searches to select and read only the pages under `pages/` needed for the learner's goal and prerequisites; reading every captured page is not required. The Markdown files are derived reading copies, not original HTML. `entry.html` is the original entry response only; original HTML for other pages is not included in this capture. Copy only referenced Markdown derivatives, together with `provenance.json` and `entry.html`, under `public/sources/<material-directory-name>/`, preserving their relative paths. In `COURSE.md` selected sources, label Markdown copies as derived reading text and pair each original page URL from provenance with its local `/sources/...` URL, noting crawler tool, date, and `entry.html` baseline; do not add source-accounting paragraphs to lesson prose. Do not claim copying a derivative preserves original HTML, and do not copy every crawled page into the site. Record pages read in `COURSE.md`. HTTP HTML records without `crawl`, or with `crawl.fallback`, are single-page sources; do not describe them as a complete documentation capture.

Find the sources yourself. First read the saved landing page and `provenance.json` (if present). Follow clues on the page and hints printed during preparation (documentation index, `llms.txt`, Markdown version, navigation, linked source repo, fallback notes) to judge what additional pages are needed, using your own tools (web reading, browser, bash/curl, etc.) to inspect candidate pages. Save what you rely on: any page relied upon to support lesson facts or to `{{cite}}` must be saved as material first. Run `npm run school -- supplement SCHOOL_NAME --source URL [--source URL …]` from the repository root (local file paths accepted). For full same-domain recrawling, run `supplement` without `--source` (pass `--crawl-prefix` only if explicitly requested). Then re-read `inputs/SCHOOL_NAME.json` (or `GENERATION.md`) for new `material-N` paths. Pages only read but not saved cannot serve as factual ground or be cited. Running `supplement` (which updates `inputs/SCHOOL_NAME.json`, `school.settings.json` materials/sources, and adds `materials/material-N`) is the only exception to the opening rule against modifying anything outside the output school and to item 7's rule against changing school.settings.json; never manually edit those files or manually create `material-N`. If saved sources remain insufficient for the learning goal after supplementing, narrow course scope to what saved sources support, record actual source scope and gaps in `COURSE.md` under selected sources and uncertainties, and do not use model memory to fill in details or attach citations. When saved sources cannot support the requested breadth or number of lessons, narrowing scope takes precedence over the request; say so in `COURSE.md`. General explanations, analogies and prerequisite background may come from your own knowledge when not presented as the source's claim. Source-specific facts — product/API/component names, options, flags, commands, file paths, versions, numbers, defaults and behavior — must come from saved sources; if no saved source supports one, leave it out.
3. Design a coherent learning path around the learner's goal, prior knowledge, and requested depth. Each lesson should address a distinct, meaningful learning objective, with clear boundaries and natural progression. Avoid overloaded lessons, unnecessary fragmentation, repetition, and repackaging the source's original structure. Keep learner-facing content focused and readable, leaving adaptive explanations and deeper exploration to the teacher. Use however many lessons the goal and requested depth need. Do not require a creator or expert to write or review each lesson. In the output school's COURSE.md explain the goal, prerequisites, capabilities, why each lesson exists, its dependency on earlier lessons, the selected sources, exclusions and reasons, uncertainties, wanted interactions (see item 6), and how to adjust the route. Explicitly explain how depth/background/learning preferences affected the scope, prerequisites, explanations, activities and expected outcomes. Include a concise source ledger connecting major claims to actual source locations. State which files you actually read. Never say you read the entire repository if you did not.
4. Write COMPLETE lessons as plain Markdown files in src/content/lessons/, with YAML frontmatter: title, slug (kebab-case), description, order (1-based), quiz: false, agentOnly: true, sources (list of paths relative to public/sources), agentInstructions: |. The title is the public name of that lesson: what a learner studies, in the course language. Do not include the school directory slug, a "Lesson N" or "第N关" prefix, the brand "Learn Islands", or the genre phrase "AI 互动课程". A textbook section can be named for its idea, as in "正数和负数：概念、例题与练习". Body must be complete, usable learning material, not an outline or a fixed checklist. Choose its content and organization to serve the lesson objective. Use only Markdown, no JSX/HTML expressions. Code fences are allowed. Use `$...$` for inline math and `$$` blocks for display math, with the opening and closing `$$` each on their own line. Keep Chinese explanations and units outside math mode. Write a literal dollar sign as `\$`. Keep code and commands in inline code or fenced code blocks. Do not repeat the lesson title as a `#` heading in the body; start sections at `##` and subsections at `###` hierarchically, without skipping levels or using bold paragraphs as headings. Keep code blocks standalone rather than nested in list items; for sequential steps, write an explanatory paragraph followed by a code block. Do not use spaces to align diagrams that mix CJK and Latin text in code blocks; represent workflows using ordered lists, tables, or `mermaid` diagrams.

When a learner-facing sentence states a source-supported key point or difficult point, mark only the short phrase that carries that claim. Do not mark an analogy, a course-written example, a claim about what is currently popular, or anything the saved source does not say. Put this marker in the lesson body as plain text, not HTML:

{{cite 短词 | path: material-1/pages/example.md | heading: Section title | url: https://example.com/docs/page | quote: The exact sentence copied from that saved file.}}

The visible phrase is at most 40 characters. path is relative to public/sources, contains no spaces, and is already listed in that lesson's sources. heading is the section title as it appears in that file. url is the original http or https page URL. quote is one exact sentence from that file, at least 20 characters, copied rather than paraphrased. The quote must itself state the marked claim; a sentence that is merely on the same page or topic is not support. If no saved sentence states it, do not mark it, and reconsider whether the claim belongs in the lesson. Do not put }} in any field. Do not put | in the phrase, path, heading, or url. Do not put a marker in a heading, table, code span, or code fence. The page renders the phrase as a source card on the self-read view. The teacher still reads the saved file; the marker is not a substitute for agentInstructions.
5. agentInstructions are flexible, HARNESS-NEUTRAL teaching notes, not an exhaustive script. Include only lesson-specific capabilities, necessary source passages to read, relevant prerequisites and misconceptions/hints, a domain-appropriate activity, expected reasoning where needed, and an observable completion condition. Activities can be prediction+observation, a numerical calculation, explaining a diagram, or tracing a mechanism. Completion means participating in the activity and receiving feedback, not scoring perfectly. Do not demand installing/building an entire source project just to learn a concept. Do not repeat shared teaching behavior, progress GET/PUT instructions, model metadata, or harness-specific tool instructions, transport, or internal session details; the shared runtime protocol supplies these. Keep actual code/library names in source material, even if they happen to match a harness name.
6. Use diagrams, visualizations, worked examples, or interactive artifacts when they materially improve understanding; choose the simplest representation grounded in sources (not required for every lesson). Store artifacts under `public/activities/` and reference them from lessons. Clearly label model-generated examples as examples, not source. Avoid fake implementations teaching false mechanisms and remote sandboxes; simple Node/Python calculations suffice. Optional browser examples may use installed dependencies if an alternative remains available. Verify executable examples.

   **Interactive blocks**:
   - **Purpose and general rules**: Interactive blocks let learners predict outcomes, tweak controls, and observe changes across any subject; any course may use any block wherever it genuinely helps (signals like counter-intuitive outcomes, tweakable parameters, or spatial relationships are examples, not limits). If none fits, use none; consider a predict or run block when the learner can observe real output; no block is better than a simulated one. Typically use at most 2–3 blocks per lesson; exceeding 3 is flagged for human review. State takeaways directly in lesson prose so reading text alone remains complete without running blocks ("the answer is on the face of the puzzle"). Block content must match surrounding text and sources without untaught concepts. Blocks render only with island chrome. Validation rejects invalid block format, execution errors/timeouts, code requiring input, run blocks producing no stdout, disallowed imports/exports/require()/dynamic import(), interactive blocks in non-island chrome, and mixing React with Preact. Non-blocking warnings flag html preview external http(s) assets, lessons with >3 interactive blocks, programming courses lacking interactive blocks, and non-programming courses using html preview demos for human review; Wanted interactions are collected to guide new component development. Self-check via `node scripts/verify-lesson-blocks.mjs schools/NAME`.
   - **predict**: Fenced `predict` blocks create "predict then reveal" cards for any discipline. Place before explaining the tested rule or test a case whose answer is not verbatim in prior text; never repeat the preceding sentence. Format: required `question: <question>`, optional `choices: <choice 1> | <choice 2>` (2–5 options separated by `|`, escaping literal pipes as `\|`), required `answer: <answer>` (must match a choice if choices present, escaping `\|`), and required `explain: <explanation>` (can span multiple lines). State the underlying principle or fact in `explain:`.
   - **run**: Fenced `python run`, `javascript run` (or `js run`), and `typescript run` (or `ts run`) blocks execute self-contained deterministic browser code, producing observable output via `print` (Python) or `console.log` (JS/TS). A run block's output must be computed by code the learner can read and change. If the real code cannot run in this runtime (framework components, CLIs, servers, config files), do not simulate it with prints; use a plain code fence with a predict card, or no interactive block. Validation rejects `import`, `export`, `require()`, Python `>>>` prompts (use regular `python` blocks), `input()`, runtime errors, timeouts, and blocks without stdout. Do not use DOM, network, or filesystem access (runtime lacks them). Because TypeScript execution strips types without type checking, demonstrate type errors using a `predict` card with actual `tsc` diagnostics rather than a `run` block.
   - **preview**: Fenced `html preview`, `jsx preview`, and `tsx preview` blocks render live browser pages and components. `html preview` blocks contain HTML, CSS, and vanilla JavaScript and should be self-contained; external `http://` or `https://` resources are flagged for review and recommended to be copied to `public/`. They can provide interactive demos for any discipline (e.g. sliders or controls) if concise and labeled as an example in prose. `jsx preview` and `tsx preview` blocks must export a default props-free component (`export default`), cannot use `require()` or dynamic `import()`, and may only import from their designated runtime (`react`, `react-dom/client` for React; `preact`, `preact/hooks` for Preact). Runtime is selected via explicit `react`/`preact` tag or inferred from imports (defaulting to Preact); a course cannot mix React and Preact. React courses must use the React runtime across all preview blocks, matching the source version. Because `.astro` components cannot render in browser, demonstrate an Astro template's effect using an `html preview` block of rendered HTML, stating in prose that this is the output result.
   - **numberline**: Fenced `numberline` blocks provide an interactive draggable number line for positions, ordering, distances, or symmetry on an axis. Format: required `range: <min integer> .. <max integer>` (left < right, span ≤ 40), required `points: <label>=<value> | ...` (1–3 points with unique labels on step ticks within range), optional `step: <1, 0.5, or 0.1>` (default 1), optional `show: <opposite | abs | distance>` (`distance` requires 2 points), and optional `caption: <one-line caption>`.
   - **Wanted interactions**: If an interaction genuinely aids learning but no supported block fits, record a single line in `COURSE.md` under `Wanted interactions` stating the lesson slug, desired interaction, and why. Do not force an ill-fitting block.
7. School identity, settings and profile options are already configured. Do not change infrastructure, school.settings.json, shared teaching routes, package manifests, or progress data. In school.config.ts, set only publicName and shortName. publicName is the homepage course name in the course language: specific to this goal, without the directory slug and without "Learn Islands". Chinese courses end with the genre phrase "AI 互动课程", for example "七年级数学上册 AI 互动课程" or "React 重新渲染 AI 互动课程". shortName is what remains after removing that genre phrase and the brand, still enough to tell this course from another, for example "七年级数学" or "React 重新渲染". Do not reuse another subject's name. Leave every other school.config.ts field as scaffolded. No mandatory separate interview lesson: a teacher can briefly ask background when necessary. Keep profile choices optional. Do not create exercises merely to fill a section; activities belong in lessons when sufficient. Write course prose in the requested language (Chinese by default); retain technical identifiers. Write only COURSE.md, src/content/lessons/*.md, the publicName and shortName fields in school.config.ts, and necessary public/sources/ and public/activities/ files. No new validation framework or testing scripts.
8. Self-review the full route for goal coverage, source fidelity, learnability and unnecessary material. Correct problems before finishing. Citation checks only prove that the marked verbatim quote exists in the saved files, not that other lesson content is verified; do not claim in the generation summary that course content is verified merely because checks passed. Return a concise explanation of what was generated, how it supports the goal, and what remains unverified. Do not claim real teaching or progress validation: another process will conduct that.

Infrastructure is preconfigured. All teachers receive shared teaching, source-access, profile and completion instructions via llms.txt. Website progress belongs to the School and must never be seeded by the generator. Transport details belong to the current harness integration and are not part of curriculum content. TeachingMode may change during learning without changing the curriculum depth or regenerating the route.

## 局部修订

This section is for `npm run school -- update NAME` on an existing course. It is not create, retry, or supplement. Do not call Pi, do not deploy, do not run `retry`, and do not fetch sources if `evidence/updates/<run>/changes.json` is missing.

Each source change has exactly one verdict. A new plan starts every change at `待判定`. `--prepare-only` and `--apply` reject any remaining `待判定`. The only final verdicts are:

- `无教学影响`: the change does not affect teaching. Include a `reason`. Do not edit the related lessons, or any other lesson that is not named by a `局部修订` change.
- `局部修订`: only for `kind` `changed` or `added`. `deleted`, `failed`, and `unobserved` cannot be `局部修订`; they may still be `无教学影响`, `需要重排路线`, or `暂无法判断`. Only the named lessons may be edited, and each named slug's `sources` (after stripping `snapshots/<id>/`) must already include that `change.path`. Include a `lessons` array of slugs. Keep those lessons' slug, order, and the `agentInstructions` text from `完成条件` or, if that marker is absent, `Completion condition` through the end of that field unchanged. Do not edit any other lesson. If neither marker is present, the update fails closed. Do not add a new `{{cite ...}}` marker. If one is already in that lesson and the saved sentence changed, correct only its path, heading, or quote so it still matches the lesson's sources.
- `需要重排路线`: slugs, order, completion semantics, or the learning path would have to change. Include a `reason`. Do not edit any lesson. If `routeReview` is true, do not keep `局部修订` verdicts; reclassify them as `需要重排路线` or shrink the candidate set. `routeReview` is also true when a candidate is the lowest-`order` lesson, when a changed path is a source of both that first lesson and another lesson, or when a changed path is shared by two lessons whose `order` differs by 1. Do not treat every `index.md` page as an index.
- `暂无法判断`: include a `reason`. Do not edit any lesson.

Allowed file edits are only the `局部修订` lesson files. `assertUpdateAllowed` in `scripts/generate.mjs` enforces that list; do not rely on this prompt alone. Do not change COURSE.md, school.config.ts, school.settings.json, existing `public/sources/` copies, `public/activities/`, `src/content/exercises/`, other plans' files under `public/sources/snapshots/`, slugs, order, or completion-condition text. Do not treat `.wrangler` or progress data as part of that freeze. Snapshots live under `public/sources/snapshots/<plan-id>/`. Apply retargets only sources whose verdict is `局部修订`; a lesson revised for one page must not retarget another page that is `暂无法判断` or `需要重排路线`. Apply refuses if a named lesson's full-text hash still equals `preparedLessonSha256`. Snapshot paths in `sources` still map to the original `material-N` path; the next check compares candidates against the bytes that lesson currently adopts. Unrevised lessons keep their original copies. A new `lastSeenSnapshot` is not the same as adopting that snapshot for every lesson.
